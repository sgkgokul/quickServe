2. The Problem — Why Real-Time Notifications?

🤔 The Scenario

Imagine this: A customer books a plumber. The plumber accepts. But the customer is staring at their screen seeing "REQUESTED" for the next 30 seconds because their app only checks for updates every 30 seconds (polling). In a real-time services marketplace, 30 seconds feels like forever.

We needed a way for the server to instantly push notifications to the client the moment something happens — a booking accepted, a job started, a payment received. The original approach was simple polling:

// Old approach: Poll every 30 seconds
useEffect(() => {
  const interval = setInterval(() => {
    fetchNotifications();  // GET /api/v1/notifications every 30s
  }, 30000);
  return () => clearInterval(interval);
}, []);

Problems with Polling

IssueImpact
⏰ Up to 30s delayUser sees stale status; feels like the app is broken
🔋 Wasted requests99% of polls return "no new data" — wasted bandwidth & server load
📈 Doesn't scale1000 users × 2 polls/min = 2000 requests/min even when nothing is happening
🔄 Not reactiveProvider clicks Accept → customer sees it only after next poll

3. Design Decision: Polling vs SSE vs WebSocket

We evaluated three approaches. Here's the full comparison:

FeaturePollingServer-Sent Events (SSE)WebSocket
DirectionClient → Server (pull)Server → Client (push)Bidirectional
ProtocolHTTP request/responseHTTP (text/event-stream)WS:// (separate protocol)
ConnectionNew connection per pollSingle persistent connectionSingle persistent connection
Auto-reconnectManual✅ Built-in by browser❌ Must implement yourself
LatencyUp to polling interval~Instant (50-200ms)~Instant
Server complexityLowLow-MediumHigh (state management)
Spring Boot supportDefault RESTSseEmitter (built-in)Requires STOMP/WebSocket config
Use case fitSimple dashboardsNotifications, live feedsChat, gaming, collaborative editing

✅ Our Decision: SSE (Server-Sent Events)

Why SSE over WebSocket?

  • Notifications are unidirectional — server pushes to client, client never pushes back through this channel
  • SSE works over standard HTTP — no special proxy/load-balancer config needed
  • Browser's EventSource API has automatic reconnection built in
  • Spring Boot's SseEmitter is dead simple — no STOMP broker or WebSocket handler needed
  • We don't need bidirectional communication (no chat feature in MVP)

Rule of thumb: If data only flows one way (server → client), use SSE. If both sides need to talk, use WebSocket.

4. SSE Deep Dive — How It Works

4.1 What is SSE?

Server-Sent Events (SSE) is a web standard (part of HTML5) that allows a server to push data to a browser over a single, long-lived HTTP connection. Think of it as a one-way pipe: the server keeps the connection open and sends messages whenever it wants.

📡 How SSE Works Under the Hood

  1. Client opens a regular HTTP GET request to an SSE endpoint
  2. Server responds with Content-Type: text/event-stream
  3. Server keeps the connection open (doesn't close it)
  4. Whenever the server has data, it writes to the response stream in a specific text format
  5. Browser's EventSource API parses these messages and fires JavaScript events
  6. If the connection drops, the browser automatically reconnects (typically after 3 seconds)

4.2 SSE Message Format

SSE messages follow a simple text protocol. Each message is separated by two newlines (\n\n):

// Each SSE message looks like this on the wire:
event: notification
data: {"id":"abc-123","title":"Booking Accepted","message":"Suresh accepted your plumbing request"}

event: notification
data: {"id":"def-456","title":"Payment Received","message":"Customer paid the advance"}

// A heartbeat/keepalive (comment line, starts with colon):
: keepalive

4.3 Browser-Side: EventSource API

// How the React frontend connects to the SSE stream
const token = localStorage.getItem('qs_access_token');

// Note: EventSource doesn't support custom headers!
// That's why we pass the JWT as a query parameter
const eventSource = new EventSource(
  `/api/v1/notifications/stream?token=${token}`
);

// Listen for the "connected" event (initial heartbeat)
eventSource.addEventListener('connected', (e) => {
  console.log('SSE connected:', e.data);
});

// Listen for "notification" events
eventSource.addEventListener('notification', (e) => {
  const notification = JSON.parse(e.data);
  // Update React state → UI re-renders with the new notification
  setNotifications(prev => [notification, ...prev]);
});

// Auto-reconnects on error (built-in browser behavior)
eventSource.onerror = () => console.log('SSE error, will auto-reconnect...');

⚠️ Key Challenge: Authentication for SSE

The browser's EventSource API does NOT support custom HTTP headers. This means you can't send Authorization: Bearer <jwt> like you do with regular API calls.

Our solution: We modified JwtAuthFilter to also check for a ?token= query parameter as a fallback. This way, the SSE endpoint can be authenticated even though EventSource can't set headers.

// JwtAuthFilter.java — extractToken method
private String extractToken(HttpServletRequest request) {
    // 1. Try Authorization header first (normal API calls)
    String bearerToken = request.getHeader("Authorization");
    if (hasText(bearerToken) && bearerToken.startsWith("Bearer ")) {
        return bearerToken.substring(7);
    }
    // 2. Fall back to query param (SSE EventSource)
    String tokenParam = request.getParameter("token");
    if (hasText(tokenParam)) {
        return tokenParam;
    }
    return null;
}

5. Kafka from Scratch — What, Why, How

5.1 What is Apache Kafka?

Kafka is a distributed event streaming platform. In simple terms, it's a super-fast, reliable "message pipe" that lets different parts of your application communicate without knowing about each other.

🎯 Real-World Analogy

Think of Kafka as a newspaper printing press:

  • Publisher (Producer): Writes articles and sends them to the press
  • Newspaper (Topic): A named channel — e.g., "Sports News", "Tech News"
  • Pages (Partitions): Articles in a topic are split across pages for parallel reading
  • Subscribers (Consumers): People who subscribe to specific newspapers
  • Subscription group (Consumer Group): A family shares one subscription — only one person reads each article (no duplicates)

The key insight: The publisher doesn't know or care who reads the newspaper. New subscribers can join anytime without changing anything about the publisher.

5.3 Why Kafka Here? (Not Overkill?)

For a single-server app, you might think Kafka is overkill. You could just call notificationService.createNotification() directly from the Booking service. And that's exactly what we also do! But Kafka teaches critical concepts:

❌ Without Kafka (Tight Coupling)

// BookingService.java
public void acceptBooking() {
  booking.setStatus(ACCEPTED);
  bookingRepo.save(booking);

  // Direct dependency on every downstream service:
  notificationService.notify(...);
  emailService.sendEmail(...);
  analyticsService.track(...);
  smsService.sendSms(...);

  // Adding a new service = changing BookingService!
}

✅ With Kafka (Loose Coupling)

// BookingService.java
public void acceptBooking() {
  booking.setStatus(ACCEPTED);
  bookingRepo.save(booking);

  // Just publish one event — done!
  kafkaProducer.publish(event);

  // BookingService doesn't know/care
  // who consumes this event
}

// Each consumer is independent:
// NotificationConsumer → creates notification
// EmailConsumer → sends email (future)
// AnalyticsConsumer → tracks metric (future)

6.3 Java Configuration — KafkaConfig.java

@Configuration
public class KafkaConfig {

    @Value("${spring.kafka.bootstrap-servers}")
    private String bootstrapServers;

    // PRODUCER: Sends messages (Java object → JSON → Kafka)
    @Bean
    public ProducerFactory<String, Object> producerFactory() {
        Map<String, Object> config = new HashMap<>();
        config.put(BOOTSTRAP_SERVERS_CONFIG, bootstrapServers);
        config.put(KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        config.put(VALUE_SERIALIZER_CLASS_CONFIG, JsonSerializer.class);
        return new DefaultKafkaProducerFactory<>(config);
    }

    @Bean
    public KafkaTemplate<String, Object> kafkaTemplate() {
        return new KafkaTemplate<>(producerFactory());  // This is what we inject to send messages
    }

    // CONSUMER: Reads messages (JSON from Kafka → Java object)
    @Bean
    public ConsumerFactory<String, Object> consumerFactory() {
        Map<String, Object> config = new HashMap<>();
        config.put(BOOTSTRAP_SERVERS_CONFIG, bootstrapServers);
        config.put(GROUP_ID_CONFIG, "quickserve-group");
        config.put(KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
        config.put(VALUE_DESERIALIZER_CLASS_CONFIG, JsonDeserializer.class);
        config.put(TRUSTED_PACKAGES, "com.quickserve.*");  // Security: only deserialize our classes
        config.put(AUTO_OFFSET_RESET_CONFIG, "earliest");
        return new DefaultKafkaConsumerFactory<>(config);
    }
}

🔑 Key Points About Serialization

  • Producer uses JsonSerializer → converts your Java BookingEvent object into JSON bytes
  • Consumer uses JsonDeserializer → converts JSON bytes back into a Java object
  • TRUSTED_PACKAGES → security feature: only deserialize classes from com.quickserve.* package (prevents malicious deserialization attacks)
  • auto-offset-reset=earliest → if a consumer starts for the first time, read from the very beginning of the topic (don't skip old messages)

7.2 Producer — Publishing Events

@Component
public class BookingEventProducer {

    private static final String TOPIC = "booking-events";
    private final KafkaTemplate<String, Object> kafkaTemplate;

    public void publishBookingEvent(Booking booking, String eventType) {
        BookingEvent event = BookingEvent.builder()
            .bookingId(booking.getId().toString())
            .customerId(booking.getCustomer().getId().toString())
            .eventType(eventType)
            // ... other fields
            .build();

        // Send to Kafka — key is bookingId (ensures same booking events go to same partition)
        kafkaTemplate.send(TOPIC, booking.getId().toString(), event)
            .whenComplete((result, ex) -> {
                if (ex != null) log.error("Failed to publish", ex);
                else log.info("Published: {}", eventType);
            });
    }
}

🔑 Why bookingId as the Key?

Kafka uses the message key to determine which partition a message goes to. By using bookingId as the key, all events for the same booking go to the same partition, which guarantees they're processed in order. You never see COMPLETED before STARTED for the same booking.

7.3 Consumer — Processing Events

@Component
public class BookingEventConsumer {

    @KafkaListener(topics = "booking-events", groupId = "quickserve-notification-group")
    public void handleBookingEvent(BookingEvent event) {
        Booking booking = bookingRepo.findById(event.getBookingId());
        NotificationType type = NotificationType.valueOf(event.getEventType());

        switch (type) {
            case BOOKING_CREATED -> notificationService.createNotification(
                providerUser, booking, type,
                "New Booking Request",
                event.getCustomerName() + " requested " + event.getSubServiceName()
            );
            case BOOKING_ACCEPTED -> // notify customer
            case BOOKING_STARTED -> // notify customer
            case BOOKING_COMPLETED -> // notify customer
            case BOOKING_RATED -> // notify provider
        }
    }
}

// The @KafkaListener annotation does all the magic:
// 1. Subscribes to the "booking-events" topic
// 2. Automatically deserializes JSON → BookingEvent object
// 3. Calls this method for every new message
// 4. Manages offsets (tracks which messages have been processed)

8. SSE Implementation — Code Walkthrough

8.1 Server-Side: SseEmitterService

This is the core of the real-time push system. It manages one or more SSE connections per user (a user could have multiple tabs open).

@Service
public class SseEmitterService {

    // Thread-safe map: userId → list of active SSE connections
    private final Map<UUID, List<SseEmitter>> emitters = new ConcurrentHashMap<>();
    private static final long SSE_TIMEOUT = 300_000L; // 5 minutes

    /**
     * Called when a user opens the SSE stream endpoint.
     * Creates a new SseEmitter and registers it.
     */
    public SseEmitter subscribe(UUID userId) {
        SseEmitter emitter = new SseEmitter(SSE_TIMEOUT);

        // Add to the user's list of connections
        emitters.computeIfAbsent(userId, k -> new CopyOnWriteArrayList<>()).add(emitter);

        // Clean up when connection closes (timeout, error, or client disconnect)
        Runnable cleanup = () -> {
            List<SseEmitter> userEmitters = emitters.get(userId);
            if (userEmitters != null) {
                userEmitters.remove(emitter);
                if (userEmitters.isEmpty()) emitters.remove(userId);
            }
        };
        emitter.onCompletion(cleanup);
        emitter.onTimeout(cleanup);
        emitter.onError(e -> cleanup.run());

        // Send initial heartbeat so client knows connection is alive
        emitter.send(SseEmitter.event().name("connected").data("ok"));
        return emitter;
    }

    /**
     * Push a notification to ALL active connections for a user.
     * Called by NotificationService after saving to DB.
     */
    public void sendNotification(UUID userId, NotificationDTO notification) {
        List<SseEmitter> userEmitters = emitters.get(userId);
        if (userEmitters == null) return; // User not connected

        List<SseEmitter> dead = new ArrayList<>();
        for (SseEmitter emitter : userEmitters) {
            try {
                emitter.send(SseEmitter.event().name("notification").data(notification));
            } catch (IOException e) {
                dead.add(emitter); // Connection broken, mark for removal
            }
        }
        userEmitters.removeAll(dead); // Clean up dead connections
    }
}

🔑 Key Design Decisions

  • ConcurrentHashMap — Thread-safe because Kafka consumers and HTTP threads access this concurrently
  • CopyOnWriteArrayList — Thread-safe list that allows concurrent iteration + modification
  • 5-minute timeout — Prevents resource leaks; browser auto-reconnects after timeout
  • Dead emitter cleanup — Proactively removes connections that have silently died

8.3 Integration — NotificationService bridges DB + SSE

@Service
public class NotificationService {

    public Notification createNotification(User recipient, Booking booking,
                                           NotificationType type, String title, String message) {
        // 1. Save to database (permanent storage)
        Notification saved = notificationRepository.save(
            Notification.builder().user(recipient).booking(booking)
                .type(type).title(title).message(message).isRead(false).build()
        );

        // 2. Push via SSE (instant delivery to connected clients)
        try {
            sseEmitterService.sendNotification(recipient.getId(), NotificationDTO.from(saved));
        } catch (Exception e) {
            // Don't let SSE failures break notification creation
            // The notification is already in DB — user can fetch it later
        }

        return saved;
    }
}

✅ Reliability Pattern: DB First, SSE Second

We save the notification to the database before attempting SSE push. This ensures:

  • If SSE fails (user offline, connection dropped) → notification is still in DB, visible on next page load
  • If DB fails → we throw an error, don't attempt SSE with phantom data
  • SSE is a best-effort optimization, not the source of truth

9. Advance Payment Flow — Architecture

9.1 Why "After Acceptance, Before Start"?

We evaluated two approaches for the advance payment timing:

❌ Pay at Booking Time

  • Customer pays before a provider is confirmed
  • If provider declines → need refund logic
  • Higher drop-off rate (friction before match)
  • Customer risk: "I paid but no one accepted"

✅ Pay After Acceptance (Chosen)

  • Customer pays only after a real provider accepts
  • No refund needed on decline (no payment yet)
  • Lower friction: customer already has a confirmed match
  • Industry standard (Urban Company, TaskRabbit)

🔀 The Key Trick: Status Interception

When the provider clicks "Accept", the frontend sends PUT /bookings/{id}/accept with status=ACCEPTED. But the backend intercepts this and saves AWAITING_PAYMENT instead:

if (newStatus == BookingStatus.ACCEPTED && booking.getStatus() == BookingStatus.REQUESTED) {

}
// The provider doesn't need to know about AWAITING_PAYMENT.
// They click "Accept" → backend handles the payment gate automatically.

10. Payment Implementation — Code Walkthrough

10.1 PaymentService — The Core Logic

@Service
public class PaymentService {

    @Transactional
    public Payment processAdvancePayment(UUID bookingId, UUID payerUserId) {

        // ── STEP 1: Validate ──────────────────────────────────────────
        Booking booking = bookingRepo.findById(bookingId)
            .orElseThrow(() -> new ResourceNotFoundException("Booking", "id", bookingId));

        // Only the customer who made the booking can pay
        if (!booking.getCustomer().getId().equals(payerUserId))
            throw new UnauthorizedException("Only the booking customer can pay");

        // Must be in AWAITING_PAYMENT state
        if (booking.getStatus() != BookingStatus.AWAITING_PAYMENT)
            throw new InvalidStateException("Payment only allowed in AWAITING_PAYMENT");

        // Prevent double payment
        if (paymentRepo.findByBookingId(bookingId).isPresent())
            throw new InvalidStateException("Payment already exists");

        // ── STEP 2: Process Payment (Simulated) ──────────────────────
        // TODO: Replace with Razorpay/Stripe SDK
        String txnId = "SIM_" + UUID.randomUUID().toString().substring(0, 12).toUpperCase();

        Payment payment = Payment.builder()
            .booking(booking)
            .payer(booking.getCustomer())
            .amount(booking.getEstimatedCost())
            .status(PaymentStatus.SUCCESS)           // Always succeeds for now
            .gateway("SIMULATED")                    // Will be "RAZORPAY" later
            .gatewayTransactionId(txnId)
            .paidAt(LocalDateTime.now())
            .build();
        paymentRepo.save(payment);

        // ── STEP 3: Transition Booking ───────────────────────────────
        booking.setStatus(BookingStatus.ACCEPTED);   // AWAITING_PAYMENT → ACCEPTED
        booking.setPaidAt(LocalDateTime.now());
        bookingRepo.save(booking);

        // ── STEP 4: Notify Provider ──────────────────────────────────
        notificationService.createNotification(
            providerUser, booking, NotificationType.PAYMENT_CONFIRMED,
            "Payment Received",
            customerName + " paid the advance. You can start the job!"
        );

        return payment;
    }
}

12. Database Changes & Gotchas

🐛 Gotcha: Hibernate Can't Update CHECK Constraints

We use spring.jpa.hibernate.ddl-auto=update which auto-creates/modifies tables. But when we added AWAITING_PAYMENT to the BookingStatus enum, Hibernate did not update the existing PostgreSQL CHECK constraint on the status column.

Result: Inserting a booking with status='AWAITING_PAYMENT' threw a constraint violation error.

Fix: We had to manually drop and recreate the constraint:

-- Drop old constraint
ALTER TABLE bookings DROP CONSTRAINT bookings_status_check;

-- Create new constraint with AWAITING_PAYMENT included
ALTER TABLE bookings ADD CONSTRAINT bookings_status_check
  CHECK (status IN ('REQUESTED', 'AWAITING_PAYMENT', 'ACCEPTED',
                      'DECLINED', 'IN_PROGRESS', 'COMPLETED', 'RATED'));

-- Same for notifications type column
ALTER TABLE notifications DROP CONSTRAINT notifications_type_check;
ALTER TABLE notifications ADD CONSTRAINT notifications_type_check
  CHECK (type IN ('BOOKING_CREATED', 'BOOKING_ACCEPTED', 'BOOKING_DECLINED',
                   'BOOKING_STARTED', 'BOOKING_COMPLETED', 'BOOKING_RATED',
                   'PAYMENT_REQUIRED', 'PAYMENT_CONFIRMED'));

Lesson: Hibernate's ddl-auto=update is great for adding columns/tables, but never modifies existing constraints. In production, always use migration tools like Flyway or Liquibase.
